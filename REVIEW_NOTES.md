## 2. 🔴 Диапазон азимутов: клиент не узнаёт, что купол упёрся

**Суть.** Полный оборот физически недоступен (особенность обсерватории) — это не дефект. Но при
этом граница диапазона **не сообщается клиенту**, и астрономическое ПО считает наведение успешным.

```
азимут    0°  ->  GT-338  ->  кламп до -100  ->  купол доезжает до упора
                     драйвер: OK, возвращается
                     ПО: "наведение на 0° выполнено"
```

`SlewToAzimuth` возвращает `void`; клиент не может отличить «доехали» от «упёрлись». Он видит
`Slewing == false` и считает, что всё в порядме. Это хуже явной ошибки — ошибку видно в логе.

**Почему не исключение.** `DriverException` из `SlewToAzimuth` срывает серию наблюдений в MaximDL,
KStars, NINA, Seq; часть клиентов падает вместо обработки. Обработка ложится на каждого
пользователя — это не разумная цена.

**Почему это не «просто кламп».** `encoderStepAzimuthDegrees = 0.533` = 360°/675 зубьев — это геометрия
**полного** оборота. `±100` шагов = `±53.3°` — **совершенно другое число**, не выводящееся ни из 675,
ни из длины окружности 8500 мм. Это заглушка из `settingsInitDefault()` (помечена «TODO: remove after
eeprom»).

В системе два независимых, ничем не связанных числа: диапазон механики (зашит в C# как 360°) и лимит
прошивки (зашит в C как 100). Они не сходятся, и **пока нет замера, никто не может сказать, какое
правильное**. Это важнее самого клампа: при следующей смене редуктора непонятно, что менять.

### Упорные концевики уже реализованы

Проверено — поддержка есть, это не доработка:

* пины `LIMIT_FORWARD` / `LIMIT_REVERSE` — `firmware/source/common/definitions.h:36-41`;
* чтение — `firmware/source/limits/limits.c:38-48` (активный низкий уровень, три датчика);
* остановка мотора — `firmware/source/motor/motor.c:79-83`;
* кламп цели в `motorGoTo` — `firmware/source/motor/motor.c:128-142`.

### Предлагаемое решение

1. **Замерить** реальную дугу от упора до упора в шагах энкодера: `FC` → `GOF` → дождаться `IM == 0` →
   `GEV` (это `+N`); аналогично `GOR` → `−M`.
2. Положить `±N` в `firmware/source/settings/settings.c` как **измеренное** значение с комментарием.
3. В `Driver.cs` вынести `minAzimuth` / `maxAzimuth` в конфиг (рядом с `homePostionAzimuth`,
   `Driver.cs:76`) и **клампить азимут в драйвере до отправки команды**, логируя факт клампа
   (вариант «B»: купол в безопасной позиции, клиент получает `OK`, причина видна в trace).
4. Позже, когда появится второй клиент или надобность в UI-показателях, — вариант «C»: команда
   границ в протокол (`GS` → `0 100 -100`), чтобы клиент мог узнать рабочий диапазон
   (потребует правок во всех четырёх точках `AGENTS.md` §5).

`Azimuth` при этом продолжает возвращать **реальное** положение купола, а не заказанное — так уже
сейчас, и это правильно.

## 3. ✅ Debug-вывод идёт в тот же USART, что и протокол — ИСПРАВЛЕНО

`main.c` пишет `usartPrint("Encoder value: …")` и `usartPrintln("Forward!")` в тот же порт, который
читает драйвер. Драйвер делает `ClearBuffers()` → `Transmit()` → `ReceiveTerminated("\n")`
(`Driver.cs`), поэтому в Debug-сборке на команду `IM#` ответом приходило `Encoder value: 42` →
`Int16.Parse` → `DriverException`.

**Решение владельца:** дебаг использовался на ранней стадии, потом стал недоступен; второй UART на
плате не распаян (только для стенда). Значит — убрать, а не заводить софт-UART.

**Сделано:** удалён `-DDEBUG` из `CMAKE_C_FLAGS_DEBUG` в `firmware/CMakeLists.txt`. Сам код под
`#ifdef DEBUG` оставлен — он ничего не стоит и включается вручную
(`-DCMAKE_C_FLAGS_DEBUG="-DDEBUG"`), если появится логический анализатор или стенд с двумя UART.

Тонкость: логирование и так было под `#ifdef`, но `-DDEBUG` добавлял **сам Debug-конфигурация** —
то есть «Debug» был ровно той конфигурацией, которая ломает драйвер. Теперь обе конфигурации
работоспособны, что и проверено: L3-спайк даёт **18/18 и на Debug, и на Release**.

## 4. ✅ Драйвер не защищён от многопоточности — ИСПРАВЛЕНО

`Driver.cs:183-195` — `CommandString` делал `ClearBuffers/Transmit/ReceiveTerminated` на **общем**
поле `serialPort`, без блокировки. ASCOM-драйверы по спецификации вызываются из нескольких потоков:
приложение крутит таймер на `Slewing` (→ `IM#`) и одновременно может вызвать `AbortSlew` (→ `ST#`).
Пересечение двух транзакций = `ClearBuffers` уничтожает чужой ответ, клиент получает чужую строку.

Прошивка к этому **не готова**: буфер команд один, очереди нет (`firmware/source/usart/usart.c:79-87`),
второй пакет затирает первый молча.

**Сделано:** вся транзакция под `lock (serialPort)` в `CommandString`; терминатор `#` перенесён
туда же (`raw ? command : command + END_COMMAND_CHARACTER`), `SendCommand` больше не дописывает `#`
сам — иначе кадр получил бы два терминатора. Попутно это чинит пункт «`raw` игнорируется» из §8.

## 6. ✅ `GOF#` / `GOR#` крутили купол в обратную сторону — ИСПРАВЛЕНО

**Найдено при подготовкой к правкам, не было в первой версии файла.** Баг подтверждён под simavr
(`test_plan.md` §10.10).

`main.c:16-20` передавал в `motorStart()` «сырые» `bool`:

```c
if (checkCommand(CMD_GO_FORWARD, cmd)) {
    motorStart(true);      // true  = DIRECTION_REVERSE  ← перепутано
} else if (checkCommand(CMD_GO_REVERSE, cmd)) {
    motorStart(false);     // false = DIRECTION_FORWARD  ← перепутано
}
```

Ошибка не бросалась в глаза, потому что `DIRECTION_FORWARD = false`
(`firmware/source/common/definitions.h:14-15`) — константы инвертированы. Кнопки (`main.c:83,88`) и
`motorGoTo()` (`motor.c:131,135`) использовали константы правильно, поэтому `SlewToAzimuth` и ручное
управление кнопками работали верно, а **`GOF#`/`GOR#` по USART крутили купол наоборот**.

**Сделано:** обе команды вызывают `motorStart(DIRECTION_FORWARD)` / `motorStart(DIRECTION_REVERSE)`.

**Про тест.** `spike_check.py` не просто «падал» — он **закреплял баг как ожидаемое поведение** в двух
местах, и в шаге 5 падал с `IndexError` на пустом списке граней. Тест переписан: `GOR#` уводит
энкодер с якоря `+100` вниз (99), `GOF#` возвращает вверх (100), реле проверяется на `GOR#`
(`PB1 = 1` — то направление, которое вообще двигается с этого якоря). Прогон: 18 checks, 0 failures.

**Остаточная ловушка — закрыта.** Сигнатура `motorStart(bool)` при инвертированных константах
допускала повторение, поэтому `DIRECTION_*` переведены на enum `Direction`
(`firmware/source/common/definitions.h`), а `motorStart`/`motorToggle`/`encoderEnableCounting`
принимают его вместо `bool`.

Важно: **компилятор такую ошибку не ловит.** В C `true` — это валидное `DIRECTION_REVERSE`, и
`motorStart(true)` собирается без единого предупреждения даже с `-Wextra` (проверено). Поэтому
защита сделана в L0-гарде `tools/test_conventions.py`: он ищет литералы `true`/`false` в этих трёх
вызовах. Проверено мутацией — если вернуть баг в `main.c`, гард падает с указанием строки.

При рефакторинге всплыл второй, неочевидный баг: `motorGetDirection()` маскировал порт как
`OUTPORT(...) & (1 << MOTOR_DIR_PIN)`, то есть получал `2` при `MOTOR_DIR_PIN = 1`. Старый каст
`(bool)` случайно нормализовал `2 → 1`, а каст к enum — нет: `(Direction)2` выходит за пределы
перечислителя, сравнение с `DIRECTION_REVERSE` ломалось. Поймали L1-тесты (`test_motor.c`), которые
**не правились** — это и было доказательством, что поведение не изменилось. Теперь функция
проверяет бит и возвращает `DIRECTION_REVERSE`/`DIRECTION_FORWARD` явно.

Бинарная совместимость на уровне протокола сохранена: имена и числовые значения перечислителей те
же, что у прежних `bool`, команды и ответы не менялись — L3-спайк даёт **18/18 с неизменёнными
ожиданиями**.

## 7. 🟡 Timer1: комментарий врёт, и скорость шагов очень низкая

`firmware/source/motor/motor.c:37-41` выставлял `WGM11|WGM10` при нулевом `WGM12` → WGM=`0011` =
**Mode 3, phase correct PWM 10-bit**, а не fast PWM, как было написано в комментарии. (Проверено по
таблице WGM из даташита ATmega8 и определениям битов в `/usr/lib/avr/include/avr/iom8.h`.)

Плюс `CS00`/`CS02` — это биты **Timer0**, численно совпадающие с `CS10`/`CS12` Timer1. Работает
корректно, но читается как опечатка.

**Комментарии исправлены, предделитель — НЕ тронут:** выбор значения требует железа, а код не должен
утверждать то, что не измерено. Отдельно зафиксировано в `AGENTS.md` §4.

**Что важнее (требует стенда):** с предделителем 1024 частота шагов = `12 МГц / (2 × 1024 × OCR1B)`.
При максимуме 128 это **≈46 Гц** (или 92 Гц при переходе в fast PWM). Полный оборот — 675 шагов,
то есть **минимум 7–15 секунд** даже без рампы. Для привода через STEP/DIR это медленно на грани
срыва шагов. Первым делом стоит попробовать предделитель 256.

**Полезно для решения:** рампа от предделителя **не зависит**. `OCR1B += 2` за один вызов
`motorProceed()`, а цикл главного цикла — 40 мс, значит разгон 15→128 занимает ~2.3 с при любом
предделителе. Поднимать крейсерскую скорость можно, не трогая разгон.

## 9. ✅ `_delay_ms(40)` — это не баг, а фича. Зафиксировано

Пункт TODO «убрать delay, чтобы не пропустить команду по usart» вводил в заблуждение: механизм
потерь команд другой (буфер один, без очереди, плюс `ClearBuffers()` в драйвере), а сам delay
**является тактом рампы разгона** — `motorProceed()` вызывается раз за итерацию главного цикла, и
`OCR1B += motorSpeedStepUp` начисляется за вызов.

**Измерено под simavr** (собран вариант с удалённым delay):

| | с `_delay_ms(40)` | без |
| --- | --- | --- |
| цикл главного цикла | 39.1 мс | 1.23 мс (**×32**) |
| разгон `OCR1B` 15 → 128 | **0.377 с** | **0.007 с (×54)** |

Отсюда: убирать delay нельзя, не переведя рампу на реальное время. Для STEP/DIR-привода разгон за
7 мс почти наверняка сорвёт шаги.

**Решение владельца:** это фича, а не баг. Исправлять не надо — надо задокументировать.

**Сделано:** `TODO` в `main.c` заменён комментарием с цифрами; пункт убран из «Open TODOs» в
`AGENTS.md` и перенесён в §4 как инвариант («период главного цикла — сознательно 40 мс»). Отдельно
записано в `changelog.md` в раздел «не изменилось», чтобы никто не ждал здесь правок.
