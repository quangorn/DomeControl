## 1. What this project is

An observatory dome control system, made of three independent parts:

1. **Firmware** (`firmware/`) — C for an **ATmega8** microcontroller (12 MHz). Drives the dome motor
   through PWM, reads the encoder and the limit switches, talks over USART.
2. **ASCOM driver** (`ascom/`) — C# / .NET Framework 4.7.2 for Windows. Implements `IDomeV2` and
   turns astronomy-software requests into USART commands.
3. **Printed circuit boards** (`pcb/`) — binary Sprint Layout 6 files (`button_panel.lay6`,
   `motor_control.lay6`). Constraint: board size must not exceed **120 × 80 mm** (see `README.md`).

The USART protocol is the only contract between the firmware and the driver; [§5](#5-usart-protocol)
lists every place a protocol change has to be made.

## 3. Build and run

### Firmware (ATmega8)

The CLion setup is described in `README.md`:

1. `-DCMAKE_TOOLCHAIN_FILE=<PATH_TO_TOOLCHAIN_FILE>` — the toolchain file is **not in the repository**;
   it must be supplied externally (avr-gcc + avr-libc + avrdude).
2. Run/Debug configuration: Executable — `run.bat`, Program arguments — `$CMakeCurrentTargetName$`,
   Working directory — `$CMakeCurrentBuildDir$`.

On Linux the same `firmware/CMakeLists.txt` builds with apt's `avr-gcc` (5.4, verified): pass a
four-line toolchain file (`CMAKE_SYSTEM_NAME Generic`, `CMAKE_SYSTEM_PROCESSOR avr`,
`CMAKE_C_COMPILER avr-gcc`, `CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY`) and build into a
`firmware/cmake-build-*` directory. The last line is required — `-mmcu` is added only inside
`firmware/CMakeLists.txt`, so CMake's compiler check fails without it. Release fits in 37 % of flash
and 23 % of RAM.

The essentials from `CMakeLists.txt`:

* `MCU=atmega8`, `F_CPU=12000000`;
* `-Os -std=gnu11 -Wall -Werror`, plus the mandatory `-fpack-struct -fshort-enums -funsigned-char`;
* linking: `-Wl,--relax,--gc-sections -Wl,-u,vfprintf -lprintf_min`;
* the **Release** configuration sets `-DNDEBUG` (and drops CMake's default `-O3`). Neither
  configuration defines `DEBUG`: the `#ifdef DEBUG` trace in `main.c` writes to the same USART as
  the protocol, so enabling it makes the firmware answer `IM#` with `Encoder value: …` and the driver
  throw. Re-enable it by hand with `-DCMAKE_C_FLAGS_DEBUG="-DDEBUG"` only for bench work;
* sources are collected with `file(GLOB_RECURSE ... "source/*.c" "source/*.h")` — a new file is picked
  up automatically, but **only after CMake is re-run** (regenerate).

### ASCOM driver (Windows)

* Open `ascom/ASCOM.Altair.Dome/ASCOM.Altair.Dome.sln` in Visual Studio and build Debug/Release.
* Requires an installed **ASCOM Platform** (its assemblies are referenced) and .NET Framework 4.7.2.
* The Debug configuration enables `RegisterForComInterop`, so building registers the driver with ASCOM.
* Installer: `Altair Dome Setup.iss` (Inno Setup); requires ASCOM Platform ≥ 6.2 and `regasm`.
* Manual checks: `ascom/DomeTest`, or `Altair Dome Test.js` (WSH; requires the ProgID
  `ASCOM.Altair Dome.Dome`).

### Host checks (Linux, no build)

`tools/` (L0 guards) and `firmware/test/` (L1 suites: the production sources against the fake AVR
layer, `test_plan.md` §4–§5) run on the host, no AVR toolchain needed:

    python3 tools/test_protocol_contract.py && python3 tools/test_conventions.py
    cmake -S firmware/test -B firmware/cmake-build-test && cmake --build firmware/cmake-build-test
    ctest --test-dir firmware/cmake-build-test --output-on-failure

Keep the build in `firmware/cmake-build-test/`, the only `.gitignore`d path ([§8.11](#8-pitfalls)).
Green proves the contract and the code's intent (which register bit is written), **not** the firmware:
only `avr-gcc` and the hardware can, and the host build does not replace the Windows build.

### Agent environment limits

`gcc`, `cmake`, `python3` (+ `pyserial`), `avr-gcc` 5.4 + `avr-libc`, and `simavr` + `libsimavr-dev`
(headers, `libsimavr`, `libsimavrparts`) are installed: the firmware **can** be built and run under
simavr here. **Not** installed: `avrdude` (flashing only), `dotnet`, `msbuild`, `mono` — the ASCOM
driver cannot be built or verified here. The L3 harness bridges the emulated USART through a pty; the
agent sandbox denies `/dev/ptmx`, so there it uses the harness's fallback UDP bridge. Never claim a
change was verified by a build that did not run.

## 4. Firmware architecture

One pattern for every module (`buttons`, `encoder`, `led`, `limits`, `motor`, `settings`, `usart`):

* `xxxInit()` — called once in `main()` before `sei()`;
* `xxxProceed()` — called from the main loop by modules that need periodic updates
  (`limitsProceed()`, `motorProceed()`);
* getters/predicates — `xxxGetValue()`, `xxxIsMoving()`, `xxxIsForwardPressed()`;
* module state lives in `static` variables inside the `.c`; only functions are exposed.

`main.c` is the only orchestrator: it polls `usartGetReceivedCommand()`, hands the command to
`static void processCommand(const char* cmd)` (the `if / else if` chain using `checkCommand()`), reads the
buttons, then calls `limitsProceed()` and `motorProceed()`.

**The main loop period is `_delay_ms(40)`, deliberately.** `motorProceed()` runs once per iteration and
the `OCR1B` ramp is applied per call, so the delay *is* the ramp clock, not just command latency —
measured under simavr, 15 → 128 takes 0.377 s with it and 0.007 s without, a 54× jump that would
stall a STEP/DIR drive. It also sets the limit-switch poll rate. Shortening or removing it is only
safe once the ramp runs off a real timebase (Timer0 or a cycle counter).

Details that matter when editing:

* **MCU pins** are defined only in `common/definitions.h` (port letter + bit number). Access goes
  through the `OUTPORT/INPORT/DDRPORT` macros from `common/utils.h`. Do not hard-code registers in
  modules.
* **Motor**: Timer1, phase correct PWM 10-bit (WGM = `0011`; `OC1B`, PB2, is the step output), PB1 is
  direction. Prescaler 1024 (`CS00`/`CS02` in `motor.c` are the Timer0 names for Timer1's `CS10`/`CS12`).
  The current speed is the `OCR1B` register. PWM is enabled/disabled through the `COM1B1` bit as the
  motor starts and stops. Ramping uses `settings.motorSpeedStepUp/Down`; one `motorProceed()` call per
  main-loop iteration, so the ramp rate follows the loop and not the prescaler.
  `motorIsMoving()` is `OCR1B > settings.motorStartSpeed`, not a separate flag.
  `motorStart(Direction)` and `encoderEnableCounting(Direction)` take the `Direction` enum
  (`DIRECTION_FORWARD` / `DIRECTION_REVERSE`, defined in `common/definitions.h`). The enum replaced a
  pair of inverted bools (`DIRECTION_FORWARD` was `false`), which is how `GOF`/`GOR` ended up reversed.
  Note that C does **not** reject a bool here: `true` is a valid `DIRECTION_REVERSE`, so the L0 guard
  `tools/test_conventions.py` enforces the constants instead ([§3](#3-build-and-run)).
  `motorGetDirection()` tests the PB1 bit and returns a `Direction`; do not cast the masked port value
  to the enum, the mask is `1 << MOTOR_DIR_PIN` (2), not a `Direction`.
* **Encoder**: `INT0` on a rising edge (PD2), counting only while `encoderEnableCounting()` is active;
  the value is a signed `int16_t`, incremented or decremented according to the motion direction.
* **Limit switches**: active low (inputs with pull-ups). When one triggers, `limitsProceed()`
  **re-anchors** the encoder value: centre → `0`, forward limit → `settings.encoderForwardLimitPosition`
  (`100`), reverse limit → `-100`. The encoder position is therefore relative to the last limit switch
  that fired, not absolute.
* **Buttons**: active low; `buttonsIsForwardPressed()` returns `true` only on the transition (the
  previous state is kept internally).
* **Settings**: `struct Settings` + `settingsInitDefault()`; the values are hard-coded
  (`motorSpeedStepUp=2`, `motorSpeedStepDown=5`, `motorStartSpeed=15`, `motorMaxSpeed=128`, limits
  `±100`). There is no EEPROM storage and no command to change settings (TODO).
* **USART**: interrupt-driven receive and transmit, 115200 8N1 with double speed (`U2X`), fixed-size
  buffers. Strings are formatted with `printInt`/`parseInt` (`itoa`/`atoi`) — `sprintf` is deliberately
  not used in this project (commit "removed sprintf usage").

## 5. USART protocol

Format: a command is ASCII and ends with `#` (`END_COMMAND_CHARACTER`); a response is ASCII and ends
with `\r\n`. Speed is 115200. Command and response buffers are 64 bytes each.
`usartGetReceivedCommand()` returns the raw frame **including** the trailing `#`; the dispatcher only
ever compares prefixes, so the terminator does not affect command matching.

| Command | Response | Meaning |
| --- | --- | --- |
| `GOF` | `OK` | Rotate forward |
| `GOR` | `OK` | Rotate reverse |
| `ST` | `OK` | Stop |
| `GT<number>` | `OK` | Encoder position (for example `GT-42`) |
| `GEV` | integer | Current encoder value |
| `IOC` | `0` / `1` | Dome is on centre |
| `IM` | `0` / `1` | Motor is moving |
| `FC` | `OK` | Find centre |

An unknown command produces `Unrecognized command: <text>` (no `OK`), and the driver throws on that.

**Any protocol change must be made in all four places at once:**

1. `firmware/source/common/definitions.h` — `extern const char* CMD_...`;
2. `firmware/source/common/definitions.c` — the string itself;
3. `firmware/source/main.c` — the command dispatch branch;
4. `ascom/ASCOM.Altair.Dome/Commands.cs` (and `Responses.cs` for responses) plus the wrapper method in
   `Driver.cs`.

And update the table above.

## 6. ASCOM driver

* Namespace `ASCOM.Altair`, class `Dome : IDomeV2`, ProgID `ASCOM.Altair.Dome`, description
  "Altair Dome", assembly version `6.5.1.0`, signed with `ASCOMDriverTemplate.snk`.
* **Settings in the ASCOM Profile**: "COM Port" (default `COM5`) and "Trace Level" (default `true`).
  They are read in `ReadProfile()` and written in `WriteProfile()` (called from `SetupDialog`).
* **Logging** uses a `TraceLogger` named "Altair"; `LogMessage(...)` is called in almost every method.
  New methods should be logged the same way.
* **Communication**: `ASCOM.Utilities.Serial` at 115200. `SendCommand(cmd)` calls the public
  `CommandString(cmd, false)`, which appends `END_COMMAND_CHARACTER` (`#`), holds a `lock` on
  `serialPort` for the whole transaction (clients poll and command from different threads, and the
  firmware has a single command buffer with no queue), then does `ClearBuffers()`, `Transmit()` and
  `ReceiveTerminated("\n")`.
* Response wrappers: `SendCommandWithSimpleResp` (expects `OK`), `SendCommandWithIntResp`
  (`Int16.Parse`), `SendCommandWithBoolResp` (`!= 0`).
* **Azimuth ↔ encoder conversion** — `EncoderValueToAzimuth` / `AzimuthToEncoderValue` with the
  constants `homePostionAzimuth = 180` and `encoderStepAzimuthDegrees = 0.533` (360° / 675 teeth;
  12.58 mm per tooth, 8500 mm perimeter). `AzimuthToEncoderValue` takes the short path (delta > 180°
  → −360°); `EncoderValueToAzimuth` normalises the result into `[0, 360)`.
* **Implemented**: `SlewToAzimuth` → `GoTo`, `FindHome`/`Park` → `FindCenter`, `AbortSlew` →
  `MotorStop`. `OpenShutter`/`CloseShutter` only flip the in-memory `domeShutterState` flag — there is
  no hardware shutter control, so `ShutterStatus` lies whenever the real shutter state differs and
  `CanSetShutter` reports `false`.
* **Not implemented** (throws): `Altitude`, `Slaved`, `SetPark`, `SlewToAltitude`, `SyncToAzimuth`,
  `CommandBlind`, `CommandBool`, `Action`.
* `SetupDialogForm` lists the available COM ports and a trace checkbox; the port is saved to the
  profile on OK.

## 7. Code conventions

* Indentation: **tabs** in `firmware/`, 4 spaces in C# (Visual Studio style).
* Names: `camelCase` for functions and variables, `UPPER_SNAKE` for macros and constants, `PascalCase`
  for types and public C# members. Function names are prefixed with the module name (`motorStart`,
  `limitsIsOnCenter`).
* Firmware includes: either `"source/<module>/<module>.h"` (relative to the `firmware/` root, which is
  in `include_directories`) or `"<module>/<module>.h"` — both styles already exist; follow the style of
  the file you are editing.
* Header files use guards; historically there are two styles (`DEFINITIONS_H_` and
  `DOMECONTROL_ENCODER_H`). New files use `DOMECONTROL_<NAME>_H`.
* Comments: some firmware comments are in Russian — that is fine, keep the language of the file you
  edit. **This document is English only.**
* Commits: a short English imperative subject (`goto command added`, `settings added, motor stop on
  limits`), one logical change per commit, no `Co-Authored-By` noise.
* Language: code, identifiers and commits are English; documentation and explanations may be Russian —
  except this file.

## 8. Pitfalls

1. **No .NET in the agent's Linux environment** — the ASCOM driver cannot be built here; the firmware
   can, under `avr-gcc` and simavr ([§3](#3-build-and-run)).
2. `-Werror` together with `-Wall`: any warning breaks the build (unused parameters, signed/unsigned
   comparisons, narrowing conversions).
3. `-fpack-struct` and `-fshort-enums` are forced. If data ever travels "over the wire" or into EEPROM
   as structs, account for the packed layout and never assume alignment.
4. `checkCommand()` is a **prefix comparison** inside an `if / else if` chain. Branch order matters: a
   command that is a prefix of another shadows it.
5. `usartPrint()`/`usartPrintln()` **block while waiting for the transmit interrupt** when the buffer
   is full. Calling them before `sei()`, or with interrupts disabled, hangs forever.
6. The usable command body is **62 bytes**: with 63 bytes `usartReceivePos` wraps to 0 and
   `buffer[0] = '\0'` wipes the command; at 64 bytes the start of the buffer is overwritten.
7. The encoder is relative to the last limit switch: the absolute azimuth is only valid after `FC` or
   after a limit switch fires. `int16_t` bounds the range — if the position runs away, overflow sends
   `GoTo` in the wrong direction.
8. The limit positions (`±100`) are defaults from `settings.c`, not measured values, and the dome cannot
   rotate a full turn. `encoderStepAzimuthDegrees` in the driver assumes a 360° travel that the firmware
   never allows: `SlewToAzimuth` outside `±53°` is silently clamped by `motorGoTo` and still reports
   success. Measure the real travel before trusting either number. See `REVIEW_NOTES.md` §2.
9. The L0 convention guard does not follow `#include`: it greps the whole `firmware/source` tree, so a
   rule it enforces (`sprintf`, direction literals, module inits) is checked in files that are not
   compiled into the target as well. A file under `firmware/source/` that is not part of the build
   still has to satisfy it.
10. `pcb/*.lay6` files are binary (Sprint Layout 6); diffing them or editing them as text is pointless.
11. `bin/`, `obj/`, `out/`, `.vs/`, `.idea/`, `__pycache__/` and `firmware/cmake-build-*` are in
    `.gitignore`; never commit build artifacts.
12. `origin/main` and `origin/motor-hardware-pwm` point at the same commit: that branch has no work yet.

## 9. Open TODOs

* `settings.h`: persist settings to EEPROM (`settingsInitDefault()` is a temporary solution); there are
  no USART commands to read or write settings.
* `Driver.cs`: move the hard-coded constants (`serialSpeed`, `homePostionAzimuth`,
  `encoderStepAzimuthDegrees`) into configuration; replace the placeholder `DriverInfo` text; implement
  `CommandBlind`/`CommandBool` or consciously leave the stubs.
* There is no hardware shutter control — `ShutterStatus` always reflects an in-memory flag, and
  `CanSetShutter` reports `false`.
* `Altair Dome Setup.iss`: the installer file list still needs the driver's own support files (the DLL
  and `ReadMe.htm` are in place, taken relative to the script via `{src}`).
* The dome cannot rotate a full turn: the hard-coded `±100` in `settings.c` and the 360° assumed by
  `encoderStepAzimuthDegrees` are unrelated numbers, and the limits are unmeasured defaults
  ([§8.8](#8-pitfalls)). Measure the travel, put it in `settings.c`, and tell the client that the dome
  stopped at a boundary instead of silently reporting success. See `REVIEW_NOTES.md` §2.

## 10. Agent workflow

1. **Read the relevant files in full** before editing. For the protocol, read both sides at once
   (`firmware/source/common/definitions.*` and `ascom/ASCOM.Altair.Dome/Commands.cs`).
2. **Minimal diff**: follow the existing module pattern, do not refactor along the way, do not change
   the indentation style of files you did not otherwise touch.
3. **Contract consistency**: if you changed the protocol, walk the four-point checklist in
   [§5](#5-usart-protocol).
4. **Verification**: build if the environment allows it; otherwise do a static review (types, buffer
   bounds, `-Werror` warnings, absence of `sprintf`, absence of blocking USART calls with interrupts
   disabled) and state honestly that no build ran.
5. **Commit**: only on an explicit request from the user. Use the subject style from
   [§7](#7-code-conventions).
6. **Report**: what changed, which files, what remains unverified, which TODOs were touched.

## 11. Keeping this file up to date

AGENTS.md is part of the deliverable, not a side artifact. A stale file is worse than a missing one:
it makes every later agent session act on rules that are no longer true.

### 11.1. When an update is mandatory

| What changed in the task | What to edit in AGENTS.md |
| --- | --- |
| A firmware module or project file was added, removed or renamed | §2 (layout), §4 (architecture) |
| CMake flags, MCU, clock, toolchain or the flashing method changed | §3 |
| The USART protocol changed (command, response, format, terminator) | §5 (table + checklist), §6 |
| MCU pins, or motor/encoder/limit logic changed | §4, and §8 if new traps appeared |
| Default settings changed, or settings storage was added | §4, §9 |
| Public ASCOM members, azimuth conversion constants or profile settings changed | §6, §8 |
| The installer, assembly version or ASCOM Platform requirement changed | §3, §6, §8 |
| A `TODO`/`FIXME` in the code was closed or added | §9 |
| A new constraint, pitfall or convention appeared | §7, §8 |

### 11.2. Checklist before finishing a task

1. Walk the table in 11.1 and update the affected sections.
2. Update the "Document state" table in §0: date and scope.
3. Make sure the file contains **no claim you have not checked against the code**: paths, function
   names, constant values, pin numbers. Anything uncertain must be verified or explicitly marked as
   needing verification.
4. Check cross-section links and Markdown table formatting.
5. If the change was local to a module and nothing in 11.1 applies, leave the file alone: "always
   update" does not mean "always rewrite".

### 11.3. Editing rules

* **Write in English.** Every change to this file — including a one-line fix — is written in English,
  so the document never drifts back into a mixed or translated state.
* Keep the file **reviewable**: aim for at most ~500 lines. New material should still pay for itself
  by deleting what is stale. Do not paste code, long listings, or paraphrases of source comments.
* Do not duplicate facts that one read of the code reveals. Duplicate only what is expensive to
  reconstruct: the protocol contract, the "what lives where" invariants, environment limits, pitfalls.
* One topic, one place. When the file contradicts itself, fix it instead of adding a caveat.
* Delete stale material as readily as you add new material. A section that stopped being true is
  removed, not marked "outdated".
* Change the section structure only when clearly necessary — other sections link to it by anchor.

### 11.4. When a task cannot update this file

If a change has knowingly desynchronised AGENTS.md but the file cannot be updated within the task (no
access, or the user asked you not to touch documentation), **say so explicitly in your final answer**:
which section is stale and exactly what needs fixing. Silently leaving the file wrong is not an option.
